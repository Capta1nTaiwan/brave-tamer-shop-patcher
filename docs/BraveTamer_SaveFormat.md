## 1. 概觀：與前作（Veedramon 版）的差異

| 項目 | Anode/Cathode Tamer Veedramon 版（HK） | **Brave Tamer（JP）** |
|---|---|---|
| 存檔媒體 | SRAM 32 KB | **EEPROM 2 KB**（`.sav` 剛好 2048 bytes） |
| Save block 數 | 2 個（rotation backup） | **1 個**，位於 `0x000`，沒有備份區 |
| Block 框架 | `02` + LE16 長度 + 資料 + `03` + BE CRC-16 | **完全相同** |
| CRC 演算法 | 表格式，表在 ROM `0x3D0637/0x3D0737` | **相同演算法**，表在 ROM `0x3B1F68/0x3B2068`（可由 8 個基底值重建，見 §2） |
| Sentinel bytes | `$4000/$4FC2/$7FFF` 必須為 0 | 無此機制 |
| 文字編碼 | 大寫 `0x21+`、小寫 `0x3E+`（HK 字型） | **日文表**：數字 `0x00`、ひらがな `0x0A`、カタカナ `0x5A`、A–Z `0xB4`、a–z `0xCE`（§3） |
| 每隻數碼寶貝的核心資料 | 物種 + 已學形態列表 | **16 位「搭檔」之一** + 現在形態 + **裝入的プラグイン卡（技）×5** + PF 卡 ×4 + 12 能力值 + Lv + YP |

> 兩作用的是同一套存檔函式庫（框架與 CRC 一模一樣），所以前作的 `fix_save()` 思路可直接沿用，只是 block 只有一個、位置在 `0x000`。

## 2. 存檔框架與 CRC-16

### 2.1 框架

| 位址 | 大小 | 內容 |
|---|---|---|
| `0x000` | 1 | Magic 1 = `0x02` ✅ |
| `0x001–0x002` | 2 | payload 長度（LE16）= `0x06AC`（1708）✅ |
| `0x003–0x6AE` | 1708 | payload（遊戲狀態，本文件其餘章節） |
| `0x6AF` | 1 | Magic 2 = `0x03` ✅ |
| `0x6B0–0x6B1` | 2 | **CRC-16，big-endian** ✅（參考存檔 = `DF F0`） |
| `0x6B2–0x7FF` | 334 | 全 `0x00` padding |

CRC 涵蓋範圍 = `0x001` 到 `0x6AF`（長度欄 + payload + magic2，共 `len + 3` bytes），**不含** CRC 本身。

### 2.2 演算法（與前作相同）

```
CRC = 0
for each byte b:
    CRC = ((CRC << 8) ^ TABLE[((CRC >> 8) ^ b) & 0xFF]) & 0xFFFF
寫回：high byte 先（big-endian）
```

`TABLE` 是 ROM 內寫死的 256 項 16-bit 表（高位元組在 `0x3B1F68+i`，低位元組在 `0x3B2068+i`）。本次額外確認：

- 這張表是 **XOR-線性** 的（`T[i^j] == T[i]^T[j]` 對全部 65536 組成立），因此只要 8 個基底值就能重建整張表，**不需要 ROM**：

| i | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 |
|---|---|---|---|---|---|---|---|---|
| `T[i]` | `8911` | `1223` | `2446` | `488C` | `8110` | `0221` | `0442` | `0884` |

- 它**不是**任何標準 CRC 多項式的表：對全部 65536 個 16-bit 多項式、MSB/LSB 兩種方向、加上索引/值位元反轉的變體暴力比對，皆無吻合。前作文件稱之為「poly 0x8911」只是因為 `T[1] = 0x8911`，實際上是遊戲自訂的線性表。`bt_save.py` 內嵌上表並在給定 ROM 時自動與 ROM 表比對。

驗證：對參考存檔計算得 `0xDFF0`，與儲存值一致 ✅。

## 3. 文字編碼（日文）

名字欄位（テイマー名、數碼寶貝暱稱）與 ROM 內名字表共用同一套 1 byte 編碼。以下是從 ROM 的**名字輸入鍵盤排列表**（`0x37005C` ひらがな、`0x370114` カタカナ、`0x3701CB` 英數）直接讀出的配置，並用 `もんざえモン`、`リョウ`、`ウォーグレイモン` 等實例驗證 ✅：

| 範圍 | 內容 | 說明 |
|---|---|---|
| `0x00–0x09` | `0`–`9` | 數字 |
| `0x0A–0x37` | あいうえお…わをん（46） | ひらがな五十音順 |
| `0x38–0x50` | がぎぐげござじずぜぞだぢづでどばびぶべぼぱぴぷぺぽ（25） | ひらがな濁音・半濁音 |
| `0x51–0x59` | ぁぃぅぇぉゃゅょっ（9） | ひらがな小字 |
| `0x5A–0x87` | アイウエオ…ワヲン（46） | カタカナ五十音順（モ=`0x7C`、ン=`0x87`） |
| `0x88–0xA0` | ガ…ポ（25） | カタカナ濁音・半濁音（ド=`0x96`、ブ=`0x99`） |
| `0xA1–0xA9` | ァィゥェォャュョッ（9） | カタカナ小字（ョ=`0xA8`） |
| `0xAA` | ヴ | |
| `0xAB` | ー | 長音 |
| `0xB4–0xCD` | `A`–`Z` | |
| `0xCE–0xE7` | `a`–`z` | |
| `0xED` | `=`（ムーン=ミレニアモン） | 名字表中出現 |
| `0xF0–0xF3` | 等級符號 ①②③④（PF 卡名） | 實際圖塊不明，工具以 ①–④ 呈現 |
| `0xFF` | 字串結束 / 填充 | 名字欄以 `FF` 結尾，其餘補 `FF` |

名字欄固定 **6 bytes**：最多 5 個字 + `FF`。預設暱稱若原名超過 5 字會去掉「モン」（モノドラモン → `モノドラ`、アルマジモン → `アルマジ`）。

> 對話文字用同一張表，但另有控制碼（`0xFC`/`0xFD`/`0xFE` 換行與強調、`0xAC–0xAF` 標點、`5C xx yy FD` 名字字典代入）。修改存檔只需要名字這部分。

|---|---|---|---|
| `+0x00` | 1 | 有效旗標 = `01` | ✅ |

| `+0x03–0x04` | 2 | LE16 物種 ID：**現在的形態**（モノドラモン 256、ギルモン 240、ブイモン 190） | ✅ |
| `+0x05` | 1 | **搭檔索引 0–15**（哪一位動畫角色的搭檔；附錄 B） | ✅ |
| `+0x06–0x0B` | 6 | 暱稱（§3） | ✅ |
| `+0x0C–0x29` | 30 | **戰鬥用能力值區塊**（現在值／基準值，見下） | ✅ 結構 |

### 尾段 14 bytes（`+0x5F`；倉庫記錄為 `+0x32`）

```
03 00 00 | LV | 31 | YP YP YP YP | 05 | XX XX | 04 00
```

| 位置 | 內容 | 信心 |
|---|---|---|
| `03 00 00` | 常數 | ❓ |
| `LV` | **等級**（觀察 3–99；ゴマモン = 99 恰為上限）。遊戲有「レベルアップ」訊息 | ⚠️ |
| `31` | 常數 `0x31` | ❓ |
| `YP` | **LE32，上限 99999**。16 隻中 5 隻恰為 99999（沒用過／放倉庫的），其餘 74k–96k。遊戲內：「**YPが0になるとタイカ（退化）**」「あずかってるあいだにYPがへらない」「デフラグ：YPをすこしカイフク」 | ⚠️（強）：**YP = 每隻數碼寶貝會消耗的「壽命值」，歸零就退化** |
| `05` | 常數（= プラグイン卡槽上限 5？） | ❓ |
| `XX XX` | LE16，觀察 8–217 | ❓ 可能是經驗值餘量 |
| `04 00` | 常數（= PF 槽上限 4？） | ❓ |

> 這 14 bytes 屬於**該筆記錄的尾巴**而非下一筆的開頭：證據是倉庫最後三筆アルマジ（其中兩筆 flag=00 的殘留副本）連尾段都完全相同，且最後一筆之後仍跟著一份相同尾段。

## 7. 12 個能力值的定義

順序與意義來自 ROM `0x372FBC` 起的**狀態畫面說明文字**（ヘルプ），並與存檔 12 × LE16 一一對應；縮寫來自 PF 卡「PFー○○プラス」與對話（`EXPP`、`YPPP`、`PAPP`、`TAPP`）：

| # | 遊戲縮寫 | 說明文字（原文） | 意義 | 參考存檔觀察 |
|---|---|---|---|---|
| 1 | **HP** | ヒットポイント／たいりょく | 體力 | 368–858 |
| 2 | **DP** | ぎりょく／ワザをつかうためにひつようなのうりょく | 技力（MP） | 235–335 |
| 3 | **AP** | こうげきりょく | 攻擊力 | 37–82 |
| 4 | **PP** | ぼうぎょりょく | 防禦力 | 27–57 |
| 5 | **SP** | ツウジョウこうげきをよけるためのすばやさ | 迴避普通攻擊的速度 | 1–46 |
| 6 | **LP** | ケガをしないようにするためのちゅういぶかさ | 避免受傷（ケガ）的注意力 | 全員 70 |
| 7 | **PA(PP)** | コジンこうげきワザをよけるためのすばやさ | 迴避單體攻擊技 | 10–37 |
| 8 | **TA(PP)** | ゼンタイこうげきワザをよけるためのすばやさ | 迴避全體攻擊技 | 12–33 |
| 9 | **SC(PP)** | ステータスへんかワザにたいするタイセイ | 狀態變化耐性 | 12–37 |
| 10 | **PC(PP)** | パラメータへんかワザにたいするタイセイ | 參數變化耐性 | 12–37 |
| 11 | **EX(PP)** | よりおおくのけいけん（EXP）をえるためのかしこさ | 經驗值獲得量（賢さ） | 全員 100 |
| 12 | **YP(PP)** | （YP）のへりをよくせいするチカラ | 抑制 YP 減少 | 全員 100 |

> 對話補充：「EXPPをあげるとYPのへりがはやくなる」「YPPPがへってYPのへりがはやくなる」—— 所以 EX 與 YP 抑制是彼此拉扯的百分比型參數（預設 100）。

## 8. 卡片系統：289 張卡、4 個類別、每張卡一隻數碼寶貝

### 8.1 遊戲裡的「デジモンカード」是統稱

對話：「デジモンカードって**すべてのデジモンのぶんだけある**」「オイラのデジモンカード！さいきょうのPいんしカードだぜ」。也就是：**每張卡都是某一隻數碼寶貝的卡**，而卡的「類別」決定用途。用 D-Ark 掃描敵人得到 scan data（`0x082`），到 Dアークshop 轉換成該隻數碼寶貝對應的卡；卡放在 **card holder**（`0x017`，50 格），也可以存進 Nanimon 的 **カードアルバム**（`0x0B6` 旗標）。

### 8.2 卡片 ID 空間（由 ROM 程式碼確認 ✅）

ROM `0x3C003F` 的函式把 holder 內的卡片 ID 依序減去各類數量分類（`cmp ax,0x21 / sub ax,0x21 / cmp ax,0x18 / sub / cmp ax,0x65 / sub / cmp ax,0x83`），`0x3C0000` 是反向函式（基底 `0 / 0x21 / 0x39 / 0x9E`）：

| 類別 | 說明文字前綴 | 數量 | Holder ID 範圍 | 卡片主表（4 bytes/張：LE16 價格, LE16 卡面數碼寶貝） | 說明文指標表 |
|---|---|---|---|---|---|
| 0 | **アイテムカード**（消耗道具） | 33 | `0–32` | `0x39829C` | `0x373ACA` |
| 1 | **しょうかんカード**（召喚，戰鬥中呼叫該數碼寶貝） | 24 | `33–56` | `0x398320` | （卡名 = 卡面數碼寶貝） |
| 2 | **Pいんしカード**（P因子／PF，組み込む後常駐效果） | 101 | `57–157` | `0x398380` | `0x375AEE` |
| 3 | **プラグインカード**（技，戰鬥中使用） | 131 | `158–288` | `0x398514` | `0x3780AA` |

合計 **289** 張（ID `0–288`）。四張主表連續排列於 `0x39829C–0x39871F`。`0x120`（288）同時是 holder 的「空槽」值——它與最後一張卡（プラグイン #130「ガルダモン」）撞號，實務上以 holder 的排序行為判斷：空槽永遠排在最後。

每張卡主表的第二個 word **X 是 1-based**（`0x3C00E8` 回傳 `X−1`），而 `0x3C018D`（取卡名字串）顯示它依類別有不同意義：

| 類別 | X−1 的意義 | 卡名來源 |
|---|---|---|
| アイテム | **卡面數碼寶貝**（物種 ID） | 文字子表 #9（`0x37214A`），以類別內索引取 |
| しょうかん | **被召喚的數碼寶貝**（物種 ID） | 直接用該物種名 |
| Pいんし | **卡面數碼寶貝**（物種 ID） | 文字子表 #10（`0x3725BA`），以類別內索引取 |
| プラグイン | **技 ID**：<238 查技名表（`0x3718D6`），≥238 查擴充技名表（`0x371EFA`，72 筆，index = 技ID−238） | 技名 |

技名表的索引恰好就是**物種 ID**（`tech[3]`=でんげきビリリン=ベタモン、`tech[173]`=ムゲンキャノン=ムゲンドラモン；擴充表 238–309 對應 boss 物種），所以プラグイン卡的 X−1 也可讀成「該技持有者的物種」。例子：四張回復卡フロッピーALL→ネオ→DX→EX 的卡面依序是ジャリモン→ギギモン→ギルモン→グラウモン（等級對應進化階段）；PF#0–3 HPプラス①–④ 的卡面是ボタモン→コロモン→アグモン→グレイモン；PF #91 エボリューター 的卡面是クルモン——與對話「クルモンのカードをくみこむとジョグレスしんかできる」完全吻合；**holder ID 263 = プラグインカード「カオスフレア」**（技 ID 290 = ブラストベルゼブモン的必殺技，ウイルス，Rank 6）。完整 289 張見附錄 C。

> 131 筆「プラグインカード[EE]…」說明字串（`0x3780AA`）的順序是相冊顯示順序，**不是**卡片 ID 順序；卡名請一律走上表的程式邏輯（`bt_save.Names.card_name()`）。

### 8.3 存檔中出現卡片的三個地方

| 位置 | 內容 | 值的型別 |

### 8.4 數碼寶貝記錄裡的 5 格 = 裝入的プラグイン卡（技 ID）

每筆記錄 `+0x2B`（倉庫 `+0x0B`）的 5 × LE16 是**裝在這隻數碼寶貝身上的プラグイン卡**，以**技 ID** 表示（= プラグイン卡主表的 X−1）；第 1 項同時寫在 `+0x01`。戰鬥中選 Waza 就是從這 5 格挑技來放。

> 第 1 版文件曾把這 5 格誤判為「進化形態列表」——因為技名表的索引正好等於物種 ID，數值看起來像一串究極體。修正依據：

1. 以技 ID 解讀，每隻搭檔裝的都是**自己究極體的必殺技**（Rank 5 プラグイン卡），三隻另外多裝了アトミックブラスター（全體攻擊，Rank 4）——這是典型的後期配置，而且每一個值都對得上一張真實存在的プラグイン卡（見下表）。
2. 進化與此無關：進化純粹依等級（Lv 11 成熟期／21 完全體／31 究極體，Ajora 攻略 FAQ Q3），YP 歸零則退化；存檔不需要「可進化形態」列表。
3. 攻略明載プラグイン卡是「裝在個別數碼寶貝身上、在 Joutai→Plug-in 查看、戰鬥中以 Waza 使用」的卡，建議配置也是每隻 1–2 張。
4. 尾段常數 `05` 對應 5 個技槽；PF 卡另有 4 格（`+0x35`）。

## 10. 修改流程、工具與檢查清單

### 10.1 `bt_save.py`

```bash
# 完整解讀（給 ROM 可把 ID 轉成日文名；不給也能跑）
python bt_save.py dump   "Brave Tamer.sav" --rom "Brave Tamer.wsc"

# 只驗 CRC
python bt_save.py verify "Brave Tamer.sav"

# 改完 bytes 後重算 CRC（不需要 ROM；-o 省略則原地覆寫）
python bt_save.py fixcrc "edited.sav" -o "fixed.sav"
```

### 10.2 實例 A：把「カオスフレア」卡加進 card holder

ベルゼブモン ブラストモード的卡在本作是**プラグインカード「カオスフレア」**（holder ID `263`，技 ID 290）。`Brave Tamer (ChaosFlare).sav` 就是這樣產生的——只改了 holder 區（`0x051–0x05F`）與 CRC：

```python
import bt_save
N = bt_save.Names("Brave Tamer.wsc")
cid = N.find_cards("カオスフレア")[0]                       # -> 263
s = bytearray(open("Brave Tamer.sav", "rb").read())
holder = [int.from_bytes(s[0x17 + 2*i : 0x19 + 2*i], "little") for i in range(50)]
used = sorted([c for c in holder if c != bt_save.HOLDER_EMPTY] + [cid])   # 保持升冪
holder = used + [bt_save.HOLDER_EMPTY] * (50 - len(used))
for i, c in enumerate(holder):
    s[0x17 + 2*i : 0x19 + 2*i] = c.to_bytes(2, "little")
s[0xB6 + cid // 8] |= 1 << (cid % 8)                        # 相冊旗標（這份存檔本來就有）
open("Brave Tamer (ChaosFlare).sav", "wb").write(bt_save.fix_crc(bytes(s)))
```

想「替換」而不是新增：直接把某一格的 LE16 改成 `263`，再把 50 格重新排序即可。

### 10.3 實例 B：直接把「カオスフレア」裝到モノドラモン身上（技 ID 290）

不經過 Nanomon 的商店，直接把技 ID `290` 寫進技槽，等同於已裝入這張プラグイン卡。`Brave Tamer (ChaosFlare on Monodramon).sav` 只改了 `0x174–0x175` 與 CRC，把モノドラモン的第 2 張技アトミックブラスター（242）換成カオスフレア：

```python
s = bytearray(open("Brave Tamer.sav", "rb").read())
rec = 0x147                                   # 隊伍槽 1 = モノドラモン
s[rec + 0x2B + 2 : rec + 0x2B + 4] = (290).to_bytes(2, "little")   # 技槽 2：アトミックブラスター → カオスフレア
open("Brave Tamer (ChaosFlare on Monodramon).sav", "wb").write(bt_save.fix_crc(bytes(s)))
```

想保留アトミックブラスター改成「多一張」：把 `+0x2A` 改 3、寫到 `+0x2B+4`（最多 5 張）。想讓它成為 `+0x01` 的第 1 張：同時把 `+0x01` 改成 `290`。未經實測。

# 把倉庫槽 0（0x28F）的 YP 補滿

### 10.4 檢查清單

- [ ] 輸出檔大小 = **2048 bytes**
- [ ] `0x000 = 02`、`0x001–0x002 = AC 06`、`0x6AF = 03` 未被動到

## 附錄 D：ROM 內資料表位置

WonderSwan 4 MB ROM 的 far pointer（`offset:segment`）換算：線性位址 `0x40000–0xFFFFF` ↔ 檔案位移 `0x340000–0x3FFFFF`（即 `file = linear + 0x300000`）。以下皆為檔案位移：

| 位址 | 內容 |
|---|---|
| `0x370000` | 文字子表總表（23 個 far pointer） |
| `0x37005C` / `0x370114` / `0x3701CB` | 名字輸入鍵盤排列（ひらがな／カタカナ／英數）——文字編碼的直接來源 |
| `0x3702B6`… / `0x370D30`… | 物種名字字串（`FF` 結尾、對齊偶數位址） |
| `0x370974`（238）/ `0x370F6C`（72） | 物種名字 far-pointer 表 = 物種 ID |
| `0x3718D6` / `0x371EFA` | 技名 far-pointer 表（238）／擴充技名表（72，技 ID 238–309）；索引 = 物種 ID |
| `0x37214A` / `0x3725BA` | アイテム卡名（33）／PF 卡名（101）far-pointer 表（`0x3C018D` 實際使用的卡名來源） |
| `0x372FBC` 起 | 狀態畫面 12 能力值說明文字 |
| `0x373ACA` / `0x375AEE` / `0x3780AA` | アイテム（33）／Pいんし（101）／プラグイン（131）卡說明 far-pointer 表 |
| `0x39828C` | `"BRAVETAMER_V001"` 簽名原文 |
| `0x39829C` / `0x398320` / `0x398380` / `0x398514` | 卡片主表 ×4（4 bytes/張：價格、X；X−1 = 卡面物種／召喚物種／技 ID） |
| `0x398720` | 14 bytes/筆的卡片相關表（店販／掉落？未解） |
| `0x3C0000` / `0x3C003F` / `0x3C00E8` / `0x3C018D` | 卡片 (類別,索引) ↔ ID 互轉、取 X−1、取卡名字串 |
| `0x3B1F68` / `0x3B2068` | CRC 表高／低位元組（256 + 256） |
| `0x270158` | 對話用名字字典（`5C xx yy FD` + 名字，含人名リョウ／タカト等；**不是**物種表） |
| `0x1F0000` 附近 | 對話文字（含「YPが0になるとタイカ」「クロークは15タイまで」「デジモンカードってすべてのデジモンのぶんだけある」等本文件引用的句子） |
